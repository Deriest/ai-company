# OpenCode Task Round 6: Workaround VansRouter Multi-Turn Bug — Kompres History Jadi 1 Pesan

> Role: senior backend engineer. Repo: /home/tvd/AI-Company.
> **ROOT CAUSE FINAL (verified QA langsung ke VansRouter): VansRouter return body KOSONG (200, len=0) untuk multi-turn conversation dengan pesan besar. Ini BUG upstream, bukan AIC-ADE truncate/budget.**

## Bukti (QA langsung ke VansRouter, tanpa AIC-ADE)

Model `kr/claude-sonnet-4.5` @ `http://127.0.0.1:20129/v1`:

| Test | Messages | Hasil |
|------|----------|-------|
| A | system(16k) + user("hi") | ✅ 200, len=1508 |
| B | user(16k) + user(question) | ❌ **200, len=0** (kosong) |
| C | system + 2x user 16k | ❌ 200, len=0 |
| D | 7x user 16k | ❌ 200, len=0 |
| E (opencode probe) | SINGLE message 200k | ✅ 200, len=2 |

**Pola:** VansRouter/claude combo HANYA bisa handle request dengan 1 pesan besar (atau system+1 user kecil). Begitu ada MULTIPLE pesan besar dalam history → response 200 tapi kosong. Ini menjelaskan:
- Simple chat (1 pesan kecil) → OK
- Conversation ber-history 30k+ (banyak pesan) → kosong (meski 30k < 200k)
- Probe opencode "200k SUCCESS" menyesatkan (single message)

## Workaround di AIC-ADE

Karena VansRouter tidak bisa diubah, AIC-ADE harus memastikan request yang dikirim ke upstream punya struktur yang upstream handle: **history di-kompres jadi SATU system message** (bukan banyak user/assistant messages).

### Task

1. **`backend/backend/services/chat_service.py` `chat_stream()` + `chat_completion()`:**
   - Setelah build context, JANGAN kirim `[system, user1, user2, ..., question]` (multi-turn)
   - Kirim `[system(berisi SEMUA history), user(question)]` — kompres history jadi 1 pesan system
   - Contoh format system:
     ```
     ## Conversation History
     user: Block 0: KKKK...
     assistant: ...
     user: Block 1: KKKK...
     ...
     ## Current Question
     [question terakhir]
     ```
   - user message terakhir = question (pendek, tanpa history)
   - Ini membuat total = 2 messages → VansRouter handle OK

2. **`backend/conversation/engine.py` `_handle_question_llm()` + `_handle_chat_llm()`:**
   - Sama: kompres history jadi 1 pesan sebelum kirim
   - `_apply_token_budget()` tetap dipakai (buang pesan paling tua dari history yang di-kompres)

3. **`backend/llm/provider.py` `chat()` + `chat_stream()`:**
   - Tambah helper `_flatten_history(messages)` yang: kalau > 2 messages → gabung jadi `[system(history), user(last)]`
   - Terapkan di `chat()` DAN `chat_stream()` supaya konsisten semua jalur

4. **Verifikasi bertingkat** (langsung ke AIC-ADE):
   | Context | Expected |
   |---------|----------|
   | 30k (7 msgs) | chunk keluar |
   | 100k (25 msgs) | chunk keluar |
   | 160k (40 msgs) | chunk keluar ATAU friendly error |
   | 240k (60 msgs) | friendly error "exceeds capacity" |
   | Simple chat | tetap OK (regresi check) |

5. **Unit test**: flatten_history menggabungkan >2 messages jadi 2; conversation 30k → request punya ≤2 messages

## Acceptance Criteria
