## Task

### 1. Fix logika truncate — jangan rusak conversation valid
- `backend/backend/services/chat_service.py` `chat_stream()`:
  - **HANYA truncate kalau estimated > policy.max_tokens** (hard ceiling), JANGAN truncate di 90% — itu memotong conversation yang masih muat
  - Truncate: buang pesan LAMA dari awal, PERTAHANKAN system prompt + context, jangan potong di tengah pesan
  - Setelah truncate, verifikasi `estimate_tokens()` ≤ policy.max_tokens
- `backend/conversation/engine.py` `_apply_token_budget()`: dipanggil dengan `max_tokens=1500` (line 663, 739) — **1500 terlalu kecil!** Harus pakai policy (get_context_policy / context_window dari DB), bukan hardcode 1500.

### 2. Handle error upstream 400 CONTENT_LENGTH_EXCEEDS_THRESHOLD
- Di `chat_service.chat_stream()` + `conversation/engine.py` + `llm/provider.py`:
  - Kalau response upstream 400 dengan `CONTENT_LENGTH_EXCEEDS_THRESHOLD` (atau pesan mengandung "exceeds threshold"/"content length") → **jangan tampilkan error mentah 400 ke user** → yield pesan ramah:
    `"Context terlalu besar untuk model ini. Mulai sesi baru atau minta ringkasan."`
  - Log detail (tokens, model) untuk debugging
- **PENTING:** karena upstream kadang sukses kadang 400 di >100k, strategi terbaik:
  - Policy konservatif: `effective_capacity = min(context_window, 100_000)` untuk model yang tidak terverifikasi reliable — truncate sebelum kirim
  - ATAU: kirim, dan kalau 400 threshold → truncate otomatis ke 80k → retry sekali → kalau masih 400 → error ramah
  - Pilih yang paling efisien, jelaskan di laporan
