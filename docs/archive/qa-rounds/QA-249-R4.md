## Konteks

AIC-ADE backend (FastAPI) kirim chat ke VansRouter (http://127.0.0.1:20129/v1, OpenAI-compatible, model `kr/claude-sonnet-4.5` yang di-route ke Claude).

### Masalah R4 (verified oleh QA)
- Conversation dengan history besar (40 msg x 16KB = **~160k tokens**) → response **KOSONG** (hanya `start` + `cost` + `done`, tanpa chunk), tapi **cost tetap ter-charge** ($0.19–0.22 per request)
- Token budget mechanism SUDAH ada di `backend/backend/services/chat_service.py` `chat_stream()` (line ~476-511: `estimate_tokens` + truncation) dan `backend/conversation/engine.py` `_apply_token_budget()`
- TAPI: policy untuk 200k window = `max_tokens` ≈ 183k (usable = 200k - 16k reserve). 160k < 183k → **tidak di-truncate** (logika budget "benar"), lalu dikirim penuh → upstream gagal → kosong
- Baseline QA: request LANGSUNG ke VansRouter 60k (tanpa AIC-ADE) juga response kosong → ada bottleneck di upstream/gateway/model layer

### Pertanyaan yang harus dijawab investigasi

1. **Apa ambang batas sebenarnya?** Test request langsung ke VansRouter dengan context bertahap (10k, 20k, 30k, 40k, 50k, 60k, 80k, 100k, 120k, 160k, 200k tokens). Catat: kapan mulai kosong/gagal, berapa cost, berapa latency.
2. **Di mana bottlenecknya?** VansRouter config? Model routing? Response streaming? Cek log VansRouter (`/home/tvd/docker-apps/VansRouter/`) saat request besar — apakah ada "input context length exceed" atau error lain?
3. **Berapa context window EFEKTIF model ini?** Model `kr/claude-sonnet-4.5` klaim 200k, tapi praktiknya mungkin jauh di bawah (karena combo/routing/limit upstream).
4. **Solusi paling efisien — evaluasi opsi:**
   - **A. Policy tuning:** reserve lebih besar (misal max_tokens = 50% window atau lebih kecil). Sederhana tapi boros capacity.
   - **B. Deteksi capacity nyata:** probe model sekali (test bertahap) → simpan `effective_context_window` per model → policy pakai angka itu. Akurat, sekali biaya probe.
   - **C. Error eksplisit:** kalau context > batas → jangan kirim → error jelas "context exceeds capacity (X tokens)" — TIDAK ada cost ter-charge untuk request yang ditolak di sisi AIC-ADE.
   - **D. Hard guard pre-send:** sebelum kirim, hitung token; kalau > limit → truncate ATAU error — jangan pernah kirim > limit ke upstream.
   - Rekomendasikan kombinasi paling efisien (biaya dev rendah, hemat token/cost, UX jelas). Tulis analisis singkat kenapa.
